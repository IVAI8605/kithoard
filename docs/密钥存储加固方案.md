## 0. 结论先说

1. **本机当前两种运行形态都返回「可加密」**：开发模式（`electron-vite dev`）与打包版（`dist/win-unpacked`）读到的 `app.keyStorage` 都是 `encrypted`，即 `safeStorage.isEncryptionAvailable() === true`。【已核实】
2. **代码路径没有问题**：`setApiKey` 是「调用时判断 + 成功才写 `enc:`」，从初始提交 `97333fb` 至今一字未改（逐版比对过）。所以现在再保存一次 Key，**一定会写成 `enc:`**。【已核实】
3. **库里的 `plain:` 是历史遗留**：主库与 `.bak` 都是 `plain:`、长度 40；`.bak` 的修改时间是 2026-11-08，与 0.1.0 开发期日志吻合。当时为什么判定为「不可加密」，现有日志没有记录，**无法唯一还原**。【已核实（形态）+ 未核实（成因）】
4. 结论：这件事不是「现在有 bug 在持续写明文」，而是「历史数据没迁移 + 缺少可观测性」。修复重点是**迁移、幂等、残留清理、提示**，不是改加密算法。
5. 建议放 **V1.1.3 补丁版**，不阻断 V1.2 开发，但要在下一次对外发版前完成。

## 3. 方案

### 3.1 历史 `plain:` 数据怎么迁移

**触发时机**：数据库打开之后、窗口创建之前（主进程启动序列里），只做一次扫描。

**算法**（幂等是核心）：

1. 若 `isKeyStorageEncrypted()` 为 false → 跳过迁移，只把状态暴露给设置页（现有提示已覆盖）。
2. 否则查询 `SELECT key, value FROM settings WHERE key LIKE 'source.apiKey.%' AND value LIKE 'plain:%'`。
3. 对每一行：在**一个事务**里把 `plain:<值>` 改写为 `enc:<safeStorage.encryptString(值).toString('base64')>`。
4. 提交后执行 `PRAGMA wal_checkpoint(TRUNCATE)`，再执行 `VACUUM`（VACUUM 不能在事务里）。
5. **强制刷新 `.bak`**：迁移前先复制一份 `kithoard.db.pre-key-migration-<yyyyMMdd-HHmm>` 留档（只增不删），迁移后覆盖 `.bak`，否则 `.bak` 里仍是明文。
6. 日志只记 `key migration done count=<n>`，不记键名以外的任何值。

**为什么幂等**：条件只命中 `plain:%`；已是 `enc:` 的行不会被再次包裹，重复启动时第 2 步查不到行，直接退出。不会出现 `enc:enc:` 的套娃。

**失败怎么退**：
- 迁移在事务里，任何一步抛错 → 回滚，库保持原样，只记 `ERROR key migration failed`。
- VACUUM 失败 → 不影响正确性（只是残留清理没做成），降级为 WARN，不阻断启动。
- 刷新 `.bak` 失败 → 不影响主库，WARN。
- 迁移前的留档文件 `pre-key-migration-*` 就是退路：用户可手动恢复；不自动删任何文件。

**注意**：迁移是「数据修改」，按项目红线要先备份；上面第 5 步的留档就是备份，必须在改主库之前完成。

### 3.2 `safeStorage` 不可用时怎么办

两个选项，代价不同：

| 方案 | 做法 | 好处 | 代价 |
|---|---|---|---|
| A. 明确告知 + 明文落盘（现状增强） | 保留 `plain:` 降级，设置页常驻提示「本机不支持安全加密，Key 以明文保存在本机数据库」 | 零迁移成本，功能可用；诚实 | 同一用户下的其他程序可读；备份/截图可能带走 |
| B. 不落盘，每次启动重输 | Key 只放内存，退出即失 | 理论上最安全 | 每开一次就要重填；要改设置读写、启动流程、备份导入导出、agent 可用性；用户很可能把 Key 写在便签上，实际更危险 |

**建议选 A**，理由：
- Windows 上 DPAPI 几乎总是可用（本次实测两种形态都 true）；真正不可用的机器极少。【已核实（本机）+ 推测（普遍性）】
- B 的收益是防「本机其他程序读取」，但它防不住内存抓取，也防不住用户把 Key 抄到别处；代价却是每次启动都要人工介入，对一个「打开即用」的桌面工具是体验灾难。
- 现有代码已经做到「不假装已加密」：`app.keyStorage` 会返回 `plaintext`，设置页与设置弹窗都有提示。【已核实】

**补充**：A 方案外加一条低成本加固——把 `%APPDATA%\kithoard` 目录 ACL 收紧到当前用户（安装/首次启动时设置）。这不在本次范围，列为可选项。

### 3.3 换机或换 Windows 用户后 DPAPI 解不开

现状：`getApiKey` catch 后返回空串，界面显示「未配置」。**不会崩、不会误用**，但有两个缺口：

1. **注释与实现不一致**：注释写「清空并要求重填」，实际没有删除或改写数据库里的坏值，只是每次读取都解密失败一次。【已核实】
2. **没有提示**：用户只看到「未配置」，会以为是软件坏了，而不是「Key 换了机器解不开」。

建议：
- 读取失败时记一条 WARN（只记 source id，不记值）。
- 设置页在「已配置过但解不开」时给一次性提示：「检测到旧 Key 无法解密（更换电脑或 Windows 账户后常见），请重新填写」。
- **不要自动删除坏值**：按项目数据安全红线，删除要有明确授权；用户重填时会被自然覆盖，坏值不影响功能。

**够不够**：从「不崩、不误用」看够了；从「用户能看懂发生了什么」看不够，建议补提示。改动很小。

### 3.4 备份文件剔除 Key 要不要写成硬约束

**要。** 现状已经是白名单（`EXPORTABLE_SETTINGS` 三键 + 导入侧忽略），并且有单测覆盖（`test/backup.test.ts` 里专门构造了 `plain:secret` 与 `plain:leak` 的用例）。【已核实】

建议写进 `工程规范.md` 的硬约束条目，措辞可直接用：

> 备份文件是不加密的明文 JSON；任何秘密类配置（API Key、令牌、密码）默认不导出、永不导入。新增设置键时必须显式判断是否属于秘密，并补一条「备份里搜不到该键」的单测。

理由：靠注释约束不住未来的人；写成规范 + 测试才是硬约束。
