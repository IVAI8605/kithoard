# Kithoard 栖材坞 · 工程规范

> **文档定位**：把 `版本规划.md` 里的工程约束落成「每次照着做」的动作。本文只管**怎么做、做到什么算完、证据长什么样**，不新增产品口径。
>
> **上游关系**：`版本规划.md` 是唯一上游。本文与它冲突时，一律按 `版本规划.md` 执行，并把冲突登记到本文 §10。
>
> **当前状态**：2026-11-08，项目尚无代码、无 `package.json`、无 git 仓库。本文的命令形态取自 `版本规划.md §12.1`；脚本尚未创建，落地时间见 §9。运行环境已定：目标机 `DESKTOP-PAUJCPF`（Win10 22H2）、开发机 `IVAI-PC`（Win11），配置与分工见 §11。
>
> **适用**：V0.1 起到 V1.0 的全部开发与发布动作。一次性排查、纯咨询不套用。
> **不适用**：本文不规定功能怎么做，也不替代 `版本规划.md` 的验收条目。

## 0. 先记住五条

1. **验证的分母是变更记录。** 没有分母的「都验过了」等于没验。
2. **门禁只能证明代码干净，不能证明这次改动对。** 对不对靠验证单。
3. **命令返回成功不算数。** 版本、数据条数、一条真实路径，都要读回来。
4. **发出去的包必须是验过的那一份。** 验证通过后不再重建。
5. **验不过就不发。** 真机（或干净环境）验证不过，不提交发布动作、不打 tag。

## 1. 一页纸流程

```
写变更记录条目（定分母） → 实现 → 起草验证单行 → 跑门禁 → 按风险档验证 → 关门三问 → 提交 → （发版时）出包 → 干净环境验证 → tag → Release → 装完读回 → 留回滚包
```

| # | 阶段 | 产出 | 什么时候做 |
|---|---|---|---|
| 0 | 写条目 | `CHANGELOG.md` 里一条「用户能感知的变化」 | 动手前，至少想清楚标题 |
| 1 | 实现 | 能过类型检查的小步改动 | 每步可编译 |
| 2 | 起草验证行 | 验证单里一行（前置值/操作/预期/失败长相/证据） | 实现后、验证前 |
| 3 | 跑门禁 | `GATE: PASS (...)` 一行 | 每次提交前 |
| 4 | 分档验证 | PASS/FAIL 摘要 | 低档随改动；中档随批次；高档发版前 |
| 5 | 关门三问 | 可发 / 不可发 | 发版前 |
| 6 | 提交 / tag / Release | commit、tag、安装包 | 发版时 |
| 7 | 装完读回 | 版本 + 数据基线 + 一条业务路径 | 发布后立刻 |
| 8 | 回滚预案 | 上一版包 + 回滚步骤 | 与本次包同时留 |

**日常改动不必每次都装包**：门禁过了就提交。装包与真机验证集中在发版批次，见 §3.6。

## 2. 变更记录：验证的分母

### 2.1 位置与格式（格式即契约）

文件固定在仓库根 `CHANGELOG.md`，一版一组，新版本插在最前。每组开头必须是可解析的标题行：

```markdown
## 0.2.0 — 2026-11-20 18:05

### 新增
- **A01 下载队列**：支持 1–5 并发、任务上移/下移。

### 改进
- **I01 搜索分页**：翻页后保留列表滚动位置。

### 修复
- **F01 同名覆盖**：第二次下载同名文件追加 `(1)`，不覆盖已有文件。

### 升级说明
- 数据：保留，`user_version` 1→2 自动迁移，迁移前复制 `kithoard.db.bak`。
- 文件：未完成任务保留 `.part`，升级后可继续。
- 缓存：不需要手动清理。
```

解析规则（`scripts/verify.ps1` 按此读，V0.1 建）：

- 版本标题：`^## (\d+\.\d+\.\d+) — (\d{4}-\d{2}-\d{2} \d{2}:\d{2})$`，破折号是「—」不是「-」。
- 条目：`^- \*\*([AIF]\d{2}) ([^*]+)\*\*：(.+)$`，一行一条，标题加粗，说明一句话。
- **允许脆，不允许静默**：解析到 0 条时脚本必须报「CHANGELOG: 未找到 0.2.0 的条目，请检查格式」并让门禁失败，不许生成空表当通过。

### 2.2 编号规则

| 前缀 | 含义 | 例子 |
|---|---|---|
| `A01` | 新增 | `A02 详情页署名区` |
| `I01` | 改进 | `I03 下载进度落库频率` |
| `F01` | 修复 | `F02 只读目录静默失败` |

每版从 `01` 重新开始，全版唯一。**编号是验证单、审查记录、提交信息的公共引用**，修复类提交信息写成 `修复: F02 只读目录静默失败`。

### 2.3 什么算一条

| 写进 CHANGELOG | 不写 |
|---|---|
| 用户能看见的行为变化（按钮、文案、流程、报错） | 内部重构、改名、拆文件、补注释 |
| 数据/文件/缓存行为变化（迁移、目录、清理） | 依赖小版本升级（无行为变化） |
| 权限、安装、卸载、安全拦截规则变化 | 测试代码、脚本、文档改动 |
| 用户会碰到的限制与例外 | 「优化了代码结构」这类无感描述 |

纯内部改动不进 CHANGELOG，也就不进分母；但要在验证单的「改动文件清单」里标 `N-A（内部重构）`，防止孤儿改动没人认领。

### 2.4 时间与措辞

- 时间精确到分钟，24 小时制，写在本机时区（Asia/Shanghai）。
- 不写「第 N 轮」「本阶段」这类过程词。
- 「升级说明」必须答三件事：数据保不保留 / 是否迁移 / 是否要清缓存或重装。

## 3. 验证分层：这个栈上到底跑什么

### 3.1 五道门禁（本机，每次提交前）

命令形态沿用 `版本规划.md §12.1`。统一入口预定为 `scripts/verify.ps1`（**尚未创建**，V0.1 建），`npm run gate` 预定为它的包装。

| 关 | 跑什么 | 覆盖什么 | 失败长相（真实形态） |
|---|---|---|---|
| 1 类型 | `npx tsc --noEmit -p tsconfig.node.json`，再 `-p tsconfig.web.json` | 主进程/preload 与渲染层的类型；按 tsconfig 的 `include` 覆盖新文件，不受 git 是否跟踪影响 | `src\main\db\index.ts(12,7): error TS2322: Type 'string' is not assignable to type 'number'.` + 退出码非 0 |
| 2 静态 | `npx eslint src --max-warnings 0` | 代码规则；`--max-warnings 0` 意味着 warning 也算失败 | `✖ 3 problems (3 errors, 0 warnings)` + 规则名 + 文件行号 |
| 3 单测 | `npx vitest run` | 纯逻辑：状态机、恢复表、Range 分支、文件名清洗、备份导入、错误码、日志脱敏、限流桶（`版本规划 §12.2`） | `Test Files 1 failed, 3 passed (4)`、`FAIL test\download\naming.test.ts > ...`、断言 diff |
| 4 构建 | `npx electron-vite build` | 三段（main/preload/renderer）能不能打出来 | `error during build:` / `RollupError:` + 文件位置；`out\` 不完整 |
| 5 变更记录 | 读 `package.json` 的 `version`，解析 `CHANGELOG.md` 首个版本组 | 当前版本有条目 + 两处版本号一致（见 §5.1） | `CHANGELOG: 未找到 0.2.0 的条目` 或 `VERSION: package.json=0.2.0 但 CHANGELOG=0.1.0` |

**为什么要检查版本一致**：`版本规划 §12.1` 只要求「CHANGELOG 条目存在」。本项目版本号只人工维护两处（`package.json` 与 `CHANGELOG.md`），把「两处一致」并入第 5 关，关数不变、成本几行代码。这是本文对 §12.1 的**收紧**，不回写上游也能执行。

### 3.2 输出纪律

- 全绿只打一行：`GATE: PASS (type/static/test/build/changelog)`。
- 失败打两行：`GATE: FAIL (static)` + 末尾 30 行日志。
- 完整日志写 `cache\gate-<yyyyMMdd-HHmm>.log`，不进对话、不进仓库。
- 脚本按 类型 → 静态 → 单测 → 构建 的顺序（快的前面），**第一关失败立即退出**，不浪费时间跑完。

### 3.3 本机跑不起来时的等价替换

门禁跑不起来不是「跳过」，是「换等价命令 + 留痕」。这一点在 PowerShell 上尤其要注意。

| 现象 | 先怎么判断 | 替代做法 | 留痕 |
|---|---|---|---|
| `npm run gate` 报「无法加载文件，未经数字签名」 | 看是否执行策略拦 `.ps1` | 默认用 `pwsh -NoProfile -File scripts\verify.ps1`；确需在 5.1 下跑才用 `powershell -NoProfile -ExecutionPolicy Bypass -File`。只在本次命令加参数，不改系统策略 | 写清「执行策略拦截，改用 Bypass 参数」，附一行版本信息 |
| 外部命令失败但脚本继续往下跑 | PowerShell 对 `.exe` 的非零退出码**默认不会自动抛错**（7 与 5.1 同） | 脚本里每条外部命令后判断 `$LASTEXITCODE -ne 0` 再退出；7.3+ 也可开 `$PSNativeCommandUseErrorActionPreference = $true` | 写清「需显式判断 `$LASTEXITCODE`」 |
| 不想用 `&&` 串联 | `&&` / `\|\|` 从 PowerShell 7 起可用，本机默认就是 pwsh 7 | 直接用 `cmd1 && cmd2`；仅当该脚本被固定跑在 5.1 上时，才退回逐条执行、显式判断退出码 | 写清「5.1 不支持 `&&`」，或说明该脚本为何必须跑 5.1 |
| `npx` 首次运行要联网下载 | 本地 `node_modules` 是否已装 | 先 `npm ci`，之后直接用 `npx --no-install` 或 `node_modules\.bin\` 下的可执行文件 | 写清「首次因联网改本地 bin，覆盖同一关」 |
| 某关本机确实跑不了（缺原生模块、无编译环境） | 单独跑最小用例确认是环境还是代码 | 标 `BLOCKED`，写清交给谁（后续 CI 或另一台机），**不许标 PASS** | 验证单「等价替换」栏：被替代的关、原因、替代命令、覆盖了哪几项、结果 |

### 3.4 产物检查（比门禁更容易漏）

| 检查 | 怎么做 | 不合格的样子 |
|---|---|---|
| 文件名版本 | 看 `dist\` 里安装包名是否含 `package.json` 的版本 | 名字还是上一版 |
| 产物内版本 | `(Get-Item .\dist\win-unpacked\Kithoard.exe).VersionInfo.ProductVersion`（**字段名待 V0.1 实测**） | 产品版本与文件名不一致 |
| 解包可用性 | `npx electron-builder --dir` 后直接跑 `dist\win-unpacked\Kithoard.exe` | 缺 `app.asar`、缺 `app.asar.unpacked`（sharp / FFmpeg） |
| 依赖是否打进去 | V0.4 起看 `resources\app.asar.unpacked\node_modules\sharp`；V0.5 起看 `resources\bin\ffmpeg.exe` | 开发机能跑、解包产物报 `E_FFMPEG_MISSING` |
| 多余大文件 | `dist\win-unpacked\resources\` 下不应有 `cache\`、测试夹具、`.map` 之外的大文件 | 安装包体积异常膨胀 |

**三方一致判据**：`文件名里的版本 = 产物内版本 = 运行时报告的版本`。任一不等，不发版。

### 3.5 真机 / 干净环境冒烟

| 阶段 | 在哪台机器 | 用什么 | 验什么 |
|---|---|---|---|
| V0.1–V0.3 | 目标机 | `npm run dev` 起窗口 + 手动按验收条目走 | 搜索、详情、下载、本地素材（按版本已有能力） |

### 3.6 风险分档：什么改动做到哪一步

档位由**碰到的边界**决定，不由改了几行决定。

| 档 | 碰到的东西 | 必须做到 |
|---|---|---|
| 低 | 文案、样式、图标、注释、纯文档 | 门禁 + 打开页面看一眼（截图或一句话描述） |
| 中 | 普通页面交互、列表/分页/排序、设置读写、IPC 字段增删、缓存刷新 | 门禁 + 解包产物跑一次相关路径 + 一条可观测断言 |
| 高 | 删除/回收站/隔离区、数据库迁移、安装/卸载/升级、下载状态机/Range/崩溃恢复、IPC 入参校验与安全策略、文件路径与文件名规则、API Key 存储 | 门禁 + 安装包/解包产物 + 独立数据目录或干净环境 + 前后数据基线 + 回滚包 + 回滚步骤 |

只要本版有一项是高，本版就按高档做。纯样式重构可以是低档；改三行的「删除」一定是高档。

**破坏性验证（删除/清空/覆盖）三条前置，满足其一才动手**：

1. 目标范围只含可丢弃、可重建的文件；或
2. 在独立数据目录/独立实例里做；或
3. 先做可回滚快照（清单 + 内容另存）。

三条都做不到就停手，把风险与候选方案报给用户。**门禁可以替换，数据不能。**

本项目有利条件：隔离区与回收站本来就是「只移入、可还原」，验证「该拒绝的拒绝了」不需要真删。测试产生的文件只放 `cache\测试数据\<版本>\`，不写用户 `Pictures\Kithoard`。

## 4. 验证单：每次改动交付的那张表

### 4.1 按版本一份，不是按改动一份

验证单按版本建一份：`cache\验证单\v0.2.0.md`。每次改动往里面**加一行**；它不代表「又交了一份文件」，而是当版所有改动的验收账本。

- `cache\` 是本地目录，必须进 `.gitignore`，验证单**不进仓库、不随版本发布**（`cache\` 的约定待补进 `版本规划 §4.2`，见 §10）。
- 保留策略：当前版 + 最近 3 个版本就地留着；更早的移到 `cache\验证单\归档\`，**不删除**（只移动）。
- 一次改动如果跨了多个版本（攒批发布），把行留在最终发布的那个版本文件里。

### 4.2 模板

```markdown
# 验证单 0.2.0

> 日期：2026-11-20 18:05　分支：main　门禁：GATE: PASS (type/static/test/build/changelog)
> 分母：变更记录 9 条（A01–A04 / I01–I03 / F01–F02）
> 结论：待填（可发 / 不可发）

## 一、前置检查

| 项 | 本次取值 | 怎么取 |

| 版本号 | 0.2.0 | `node -p "require('./package.json').version"` |

| 独立实例（仅高档用） | `--user-data-dir=cache\实例\v0.2.0` | 见 §10 待验证 |

| Pixabay Key | 已配置，可搜索 | 设置页 |

## 二、验证表
```

### 4.3 一行怎么写才算合格

填句公式：

> **前置**：某配置/状态 = 某值；**操作**：具体命令或具体点击；**预期**：某字段 = 某值 / 条数 / 状态码 / 界面文案；**失败长相**：出现什么就说明没通过；**证据**：命令 + 一行输出，或截图文件名。

| 不合格 | 合格 |
|---|---|
| 下载正常 | 入队 1 个 12 MB 视频，进度每 500 ms 增长；资源管理器里 `.part` 大小与界面已下载字节相差 ≤ 1 MB；失败时两者差值持续扩大 |
| 暂停能用 | 下载中点暂停，`.part` 大小 10 秒内不变；点继续后从暂停字节继续增长，且不从头开始；失败时 `.part` 归零或进度倒退 |
| 设置保存成功 | 并发数改 2 保存，杀进程重开，设置页仍显示 2；失败时回到 3 或输入框空白 |
| 界面没问题 | 不作为验收项，只算存在性冒烟 |

三条硬规则：

1. 「页面能开、控制台 0 报错、元素都在」只证明页面存在，不算行为验证。
2. 数值必须是从界面或文件系统读回来的实际值，不写「约」「大概」。
3. 每条都要写失败长相——用来区分「没验到」和「验了没问题」。

### 4.4 关门三问

发版前逐条回答，答不上就不发：

1. **分母对得上吗**：验证表编号集合 = CHANGELOG 条目编号集合，差集为空？
2. **证据是不是空的**：有没有只写「正常」「已验证」，没写命令输出或文件名的行？
3. **未验证项写清了吗**：每条都有原因、风险判断、后续安排？

## 5. 发布与回滚

### 5.1 版本号出现在哪，谁是真源

| 位置 | 谁写 | 是否人工同步 |
|---|---|---|
| `package.json` 的 `version` | 人 | **是，唯一真源** |
| `CHANGELOG.md` 首个版本标题 | 人 | **是，第二处，门禁第 5 关核对** |
| 安装包文件名 | `electron-builder` 自动取 `package.json` | 否 |
| 运行时 `app.getVersion()` | 自动 | 否 |
| 诊断日志首行 `version=`（V0.1 起） | 自动 | 否，见 §10 待回填 |
| 备份 JSON 的 `appVersion` | 自动（`版本规划 §5.7`） | 否 |
| `版本规划.md` 第 7 节的 `V0.x.0` | 人（规划编号） | 否，不参与一致性断言 |

**规矩**：全项目只有两处人工版本号。`README` 不写死版本号（V0.6 出 README 时也不写），避免出现第三处需要同步的地方。

### 5.2 tag 与产物命名

| 项 | 约定 | 状态 |
|---|---|---|
| 版本格式 | `0.2.0`（不带前缀），开发版 `0.x.y`，首个发布版 `1.0.0`（`版本规划 §2-6`） | 现在定 |
| tag | `v0.2.0`（小写 v + 版本号） | 现在定 |
| 安装包 | `Kithoard-Setup-0.2.0-x64.exe` | 预定，V0.1 落 `electron-builder` 配置时确认 |
| 解包目录 | `dist\win-unpacked\`（electron-builder 默认） | 待 V0.1 实测 |
| 产物目录 | `dist\`，进 `.gitignore`；已发布版本**只增不删** | 现在定 |
| `productName` | 是否用中文「栖材坞」待定：中文会影响安装路径与快捷方式名 | 待 V0.1 定，定了补进 `版本规划` |

`artifactName` 必须在构建配置里显式写死，不要吃默认值——默认名会随 `productName` 变，改名就断了「文件名版本」这条核对链。

### 5.3 发布顺序

与 `版本规划 §7.9` 一致，不额外加步骤：

1. **冻结**：发版批次里不再改代码；改了就作废前面已跑的验证，重跑受影响档位。
2. **全量门禁**：`npm run gate` → `GATE: PASS (...)`。
3. **出候选包**：V0.1–V0.5 用 `npx electron-builder --dir`；V0.6 起 `npx electron-builder --win nsis`。
4. **产物检查**：§3.4 三方一致 + `Get-FileHash -Algorithm SHA256` 记下哈希。
5. **干净环境/真机验证**：按验证单逐行填，只回 PASS/FAIL。
6. **关门三问**：§4.4。
7. **提交 → tag → push → Release**：附件用第 3 步那个文件，**不重新构建**；Release 说明从 `CHANGELOG.md` 该版本截取，不另写一份。
8. **装完读回**：§5.4。
9. **留回滚包**：§5.5。

「验过的包不重建」的代价是：验证期间工作区可能已有未提交改动。补偿两条——验证前把 `git status --porcelain` 存进验证单，验证期间不动源码；tag 指向的提交必须能重建出同一版本号，不要求字节完全一致（见 §8）。

### 5.4 发布后怎么读回确认

| 证据 | 读法 | 不合格的样子 |
|---|---|---|
| 运行版本 | 诊断日志首行 `version=0.2.0`（V0.1 起）；V0.6 起再看安装包属性 | 显示上一版；带 `-beta` 之类后缀；与 tag 不等 |
| 数据基线 | `kithoard.db` 的 `assets` / `local_files` / `downloads` 条数 + 库文件大小 | 条数变少、库变小、隔离区记录被清空 |
| 一条真实业务路径 | V0.1：搜一个词出 20 条；V0.2 起：下载一条后本地素材可见 | 界面正常但列表为空、字段缺失、错误被吞 |
| 启动日志 | `%APPDATA%\Kithoard\logs\` 最新文件里没有 ERROR | 有 ERROR 但界面看起来正常（最危险） |
| 产物哈希 | 本地 `Get-FileHash` 与 Release 附件对比 | 不一致 = 发的不是验过的那份 |

**「装完立刻」就是观察窗口。** 桌面交付没有生产流量可以「用几天看看」，延迟观察等于没观察。

数据库条数的读取方式还没定：V0.1 前用界面条数或临时脚本人工读，V0.2 起并入 `smoke.mjs` 输出（见 §10）。

### 5.5 回滚

**回滚包**：每版安装包留在 `dist\`，按文件名区分版本，**只增不删**。至少保留上一版；历史包不会被新构建覆盖。

**四步**：

1. 退出应用（任务管理器确认进程结束，`版本规划 §7.8-验收 9`）。
2. 卸载当前版（默认保留 `%APPDATA%\Kithoard` 与下载目录）。
3. 安装上一版包。
4. 启动，读回版本 + 数据条数 + 一条业务路径，写进验证单。

**数据库降级是回滚的真正风险点**：

- 本版若执行过 `PRAGMA user_version` 迁移，回滚到旧版前必须先用迁移前的 `kithoard.db.bak` 覆盖（`版本规划 §5.2` 规定迁移前强制复制）。
- 验证单里凡涉及新表、新列、一次性数据动作，必须加一行：「回滚到上一版后能启动、能读库」，并给出实际条数。
- **回滚救不了已写坏的数据**：删除/覆盖类操作靠「操作前快照 + 操作后对账」，以及回收站与隔离区，不靠安装包。

## 6. 文档分工

| 文档 | 路径 | 写什么 | 不写什么 | 生命周期 |
|---|---|---|---|---|
| 版本规划 | `版本规划.md` | 版本切分、每版交付与最小验收、技术选型、偏离登记、门禁总则 | 具体代码、精确日期、单条 bug 的修法 | 大改递增为 `版本规划-02.md`，不覆盖 |
| 变更记录 | `CHANGELOG.md` | 用户可感知的变化、升级说明、条目编号 | 内部重构、未发布内容、「第 N 轮」 | 长期维护，新版本插最前 |
| 验证单 | `cache\验证单\<版本>.md` | 前置检查、改动→验证项→结论→证据、等价替换、未验证项、改动文件清单 | 「正常」「已验证」「应该没问题」 | 本地留存，不进仓库、不发布 |
| 审查 / 交接 | `2026-11-08_独立审查报告.md`、后续 `审查交接-<日期>.md` | 结论、证据、未闭环项、下一步、阅读顺序 | 把历史时点的结论当今天的待办 | 明确标注时点；过期内容标「已过期」 |
| 工程规范 | `工程规范.md`（本文） | 流程、门禁、验证单、发布回滚、文档分工、运行环境基线 | 产品口径、验收条目、功能设计 | 改了写 §12 变更记录 |
| 历史归档 | `docs\archive\` | 原始需求与开发文档，供追溯 | 不作验收依据 | 只读，不再修改 |

三条防「写成空话」的判据：

1. 每条陈述都能被一条命令或一张截图证伪。
2. 区分「现状」和「要求」：还没实现的，不写成当前事实。
3. 写清「不做什么」，比写「做什么」更能防范围膨胀。

## 7. 冲突怎么处置

1. 本文与 `版本规划.md` 冲突 → **以 `版本规划.md` 为准**，本文改正，并在 §10 记一条。
2. 代码/注释/口头约定与 `版本规划.md` 冲突 → 以 `版本规划.md` 为准；要改结论，先改 `版本规划.md`（递增编号），再改本文与代码。
3. `CHANGELOG.md` 与实际行为冲突 → 视为缺陷：以「代码 + 验证单证据」为准，修 CHANGELOG 或修代码，二选一，不许两边不一致放着。
4. 归档件（`docs\archive\`）与 `版本规划.md` 冲突 → 以 `版本规划.md` 为准，归档件只用来追溯原始意图。
5. 本文未覆盖的细节 → 按「不改产品口径」的原则自行决定，事后补进本文，不要只留在聊天记录里。

## 8. 取舍记录：通用做法逐条采用 / 不采用

来源：`D:\IVAI\Documents\AI\_文档\通用工程经验与流程.md`（下称「通用文档」，取自一个单二进制、Linux 真机交付的项目）。下表逐条说明本项目怎么办。

| # | 通用做法 | 本项目 | 理由 |
|---|---|---|---|
| 1 | 先构建 → 真机验证 → 最后提交 | **只在发版批次采用** | 通用项目的验证依赖远程设备，本机就能装包验证；日常改动需要可回溯的提交点。发版时靠「冻结 + 验过的包不重建 + tag 指向冻结提交」保证一致，而不是靠「提交晚于验证」 |
| 2 | 版本号硬编码在多处，靠脚本兜底 | **不采用硬编码** | Electron 有 `app.getVersion()`，安装包名由 `electron-builder` 从 `package.json` 取。人工只维护两处，其余自动派生，比「五处硬编码 + 断言」少一半同步风险 |
| 3 | 「验证表行数 ≥ 变更记录条目数」这种机械指标 | **不采用**，改「编号集合对齐」 | 行数可以靠凑行满足；编号对齐要求每个条目都有落点，脚本能算出差集 |
| 4 | 用文本 grep 做架构断言（路径校验必须出现哪两个调用、前端不得引用某框架） | **现阶段不用**，只留三条可机读事实 | 字符串断言一重构就误报，维护成本高于收益。本栈的分层纪律（`shared` 不引 Node、`renderer` 不直接 require）由 tsconfig 的 `types`/`includes` 和 ESLint 规则挡，比 grep 稳。见 §9 触发条件 |
| 5 | 文档断言脚本（版本一致、产物被忽略、依赖数量） | **采用，缩到三条** | 版本号两处一致（并入门禁第 5 关）、`dist\`/`cache\` 在 `.gitignore`、`resources\bin\` 无多余大文件。只断言「现状」，不写「要求」 |
| 6 | 验证单从 diff + 变更记录半自动生成 | **采用，V0.2 后做** | 先手工跑顺一版，再让脚本生成骨架（编号、改动文件清单），验证项仍人写 |
| 7 | 产物字节级可复现（去时间戳、去提交号） | **不采用** | NSIS 安装包天然带时间戳，追求字节一致成本高。改用「验过的包不重建」，同样能保证「发出去的就是验过的」 |
| 8 | 五层门禁里含 CI | **暂不建 CI** | 目前没有远程仓库（2026-11-08 实测 `git status` 报 not a repository）。本机全量门禁 + 产物检查 + 真机冒烟已覆盖单机单人开发的全部风险。触发条件见 §9 |
| 9 | 每次改动都要目标环境验证 | **不采用**，改风险分档 | 桌面应用装包只要几十秒，但仍没必要每个文案改动都装一遍。按 §3.6 分档，高档改动才是每次真机 |
| 10 | 验证单不进仓库 | **采用** | 进 `cache\`，不提交；验证单是过程证据，不是产品文档 |
| 11 | 破坏性验证三条前置（可丢弃 / 独立实例 / 快照） | **采用** | 「永不物理删除、只进回收站/隔离区」与本项目 `版本规划 §5.8` 完全一致，天然好落地 |
| 12 | 变更记录格式被脚本解析（格式即契约，允许脆） | **采用** | 用固定标题格式换自动核对分母。解析 0 条必须报错，不静默 |
| 13 | Go 专属做法（`gofmt`、`GOOS` 交叉 vet、`-race`、`-buildvcs=false`） | **不适用** | 本栈的等价物：`tsc` 双项目、`eslint`、`vitest`、`electron-vite build`；没有跨平台编译问题（只做 Windows x64） |
| 14 | 时间精确到分钟、24 小时制；修复条目带编号 | **采用** | 编号是 CHANGELOG、验证单、提交信息之间的引用键 |
| 15 | 发布附件用验过的同一份文件、一个版本一个 tag | **采用** | 与 `版本规划 §7.9`「通过后才打 tag」一致 |

**一句话总结**：机制类（分母、验证单、分档、回滚包、破坏性前置）照收；与具体技术栈绑定的（硬编码版本、grep 断言、字节级复现、CI 分层）按本项目重做或暂缓。

### 11.4 由配置差异定下的五条规矩

1. **Win11 通过 ≠ Win10 通过。** 两机系统差一个大版本（26200 vs 19045），可能出差异的面：Chromium 渲染与字体、高 DPI 缩放、系统文件对话框、回收站（`shell.trashItem`）、快捷方式与任务栏、长路径。因此每个版本的真机验收项必须在目标机过一遍，本机只能做前置自查。
2. **性能只在目标机量，且要写明电源状态。** 目标机是笔记本 + 移动版显卡，插电与电池、高性能与省电模式的分数能差一倍。性能类验收（V0.4 图片批处理、V0.5 转码/压缩）的验证单必须先写「电源：已插电 / 模式：高性能」，再写耗时；两次测量条件不同就不许对比。
3. **不要用显卡推断转码速度。** FFmpeg 随包的是软编构建，CPU 编码为主，RTX 4060 不参与 V0.5 的转码耗时。目标机 CPU 是 i7-13650HX（移动版，受功耗墙影响），耗时以实测为准。
4. **目标机是单块 954 GB 盘，测试数据要克制。** 单个测试文件不超过 2 GB，总量不超过 20 GB；只落在应用自己的测试目录，不写用户 `Pictures\Kithoard`；用完按 `版本规划 §5.8` 的分类处理（应用临时文件可删，用户文件进回收站）。目标机不保证挂载 NAS，验证不得依赖网络盘。
5. **目标机是家庭版，不能拿它当「干净环境」。** 家庭版无 Hyper-V 管理器、无组策略、不能加域；它又是日常在用的机器，重装会毁掉用户环境。V0.6 的「干净环境安装/卸载」验证放在**开发机上的虚拟机**或第二台机器，目标机只做「装在自己的真实环境里能不能用」。

### 11.5 最低系统要求口径

- 实际运行环境是 **Windows 10 22H2（19045）x64**，所以「不低于 19045」是本项目必须满足的线。
- `版本规划 §3.1` 要求锁 Electron 版本后核对 **Win10 1809** 支持情况。是否真的向下兼容到 1809，取决于所选 Electron 版本的支持矩阵，V0.1 锁定版本时一并定，**不凭印象写进文档**。
- 结论定下来后回填 `版本规划.md`（见 §10.2 第 5 条），本文不再重复口径。
