## 0. 一句话结论

Agent 接口要做，但**不进 V1.0 发布范围**：先把 V0.1–V0.6 的主链路做扎实，再在 V1.1 用"默认关闭 + 最小作用域 + 人工审批 + 全量审计"的方式加一个受控入口。

## 1. 八个问题的决定

### D01 Agent 接口是否进 V1.0 发布范围

| 项 | 内容 |
|---|---|
| 决定 | **不进 V1.0**。作为 V1.1.0 能力；V1.0 前只做设计与登记（P0），默认关闭 |
| 采纳理由 | V1.0 是"需求验收 + 已签字偏离清单"的发布里程碑，作用是把现有闭环钉死。此时引入一个新的对外能力面，等于在封版前扩大回归范围；而这个能力面本身依赖 V0.2–V0.6 的能力齐备才有意义 |
| 影响 | 上游新增 6.5、7.10，7.1 总览增 V1.1.0 行；V1.0 验收条目一条不增。V0.1 期间只产出设计文档，不写接口代码 |

### D02 默认开启还是手动开启

| 项 | 内容 |
|---|---|
| 决定 | **默认关闭**。设置里显式开启，首次连接需用户确认 |
| 采纳理由 | 用户不知道存在外部入口时，任何默认开放都等于偷偷给应用开了后门。默认关闭让"是否允许外部程序操作我的素材"变成一个用户明确做过的选择 |
| 影响 | 所有工具在未开启时返回 `E_AGENT_DISABLED`；设置页需要"Agent 接入"开关与已连接客户端列表；首次连接弹确认框 |

### D03 是否允许 agent 申请删除（回收站）

| 项 | 内容 |
|---|---|
| 决定 | **允许申请，但必须人工逐次审批**；`destructive` 作用域默认不含，也不提供"永久允许" |
| 采纳理由 | 完全不给会让 agent 在"整理"这类任务上断腿；直接给则违背"用户文件只进回收站、删除必须人确认"的产品底线。审批是唯一能同时满足两边的结构 |
| 影响 | 删除不进入 agent 的作用域白名单，只能走两阶段审批；审批框必须显示数量、完整路径、字节数、能否还原；`E_APPROVAL_REQUIRED` / `E_APPROVAL_DENIED` / `E_APPROVAL_EXPIRED` 三个错误码是必需项 |

### D04 审计是否提供 UI 查看与导出

| 项 | 内容 |
|---|---|
| 决定 | **提供**查看与导出，并作为 §9.3 的新偏离登记 |
| 采纳理由 | 只写不读的审计只能用于事后取证，用户日常无法核验 agent 做了什么，等于把"可追溯"变成口号。同时它需要在上游偏离表登记，否则就是一个没根的功能 |
| 影响 | 新增审计查看入口与导出；审计文件 `agent-audit.jsonl` 需要轮转与脱敏；§9.3「不记录独立运行日志」的结论要补一条例外说明 |

### D05 是否允许读取非秘密设置

| 项 | 内容 |
|---|---|
| 决定 | **允许白名单读取**；写入仍然只走界面 |
| 采纳理由 | agent 要告诉用户"文件会下到哪"，就必须知道下载目录与并发数。读取非秘密项没有副作用；写入属于用户偏好，agent 没有正当需求 |
| 影响 | `settings_read` 只返回 `download.dir`、`download.concurrency`、`source.enabled`、`cache.retentionDays`；返回值脱敏；`settings:set` 与 API Key 永不进接口 |

### D06 批量上限是否沿用 20 条并加时间窗

| 项 | 内容 |
|---|---|
| 决定 | **单批 20 条 + 60 条 / 10 分钟时间窗** |
| 采纳理由 | 只有单批上限时，agent 循环调用就能绕过限制，等于没有上限。时间窗是唯一能防住"循环 20 条"的结构性约束，也和 Pixabay「禁止系统性批量下载」的合规要求一致 |
| 影响 | 新增 `E_BATCH_TOO_LARGE` 与 `E_QUOTA_EXCEEDED`；网关需要按客户端记录滑动窗口；文档要写明建议调用间隔 |

### D07 传输是否一开始就做本地 HTTP

| 项 | 内容 |
|---|---|
| 决定 | **后置**。先命名管道 + MCP 薄壳 + CLI 薄壳；有真实需求再开本地 HTTP |
| 采纳理由 | 开端口就会引入浏览器可达面、CORS、DNS rebinding、防火墙提示等一整套问题。命名管道没有端口，浏览器里的网页扫不到，风险面天然更小。MCP 和 CLI 已经覆盖主要使用场景 |
| 影响 | 第一阶段只实现管道；本地 HTTP 的底线要求（仅 `127.0.0.1`、校验 Host、令牌放请求头、请求体上限、可轮换吊销）写进评估报告 §3.4 备用，暂不实现 |

### D08 来源署名是否作为工具强制字段

| 项 | 内容 |
|---|---|
| 决定 | **强制**。所有素材相关返回都带 `attribution`，文档要求 agent 展示 |
| 采纳理由 | Pixabay 的接口条款要求展示来源，这是接入合法性的基础，不是可选的 UI 细节。agent 侧如果不强制，用户看到的就是"无来源素材"，合规基础直接不成立 |
| 影响 | `search_assets`、`get_asset` 等返回结构里 `attribution` 为必填；工具文档与错误回退模板中写明"不得省略署名"；单测断言缺失署名时不得返回成功 |

## 2. 附带拍板的工程决策

### D09 IPC handler 函数体下沉为 service

| 项 | 内容 |
|---|---|
| 决定 | 作为 **V0.2 的前置批次**执行，排在 V0.1 收尾之后、V0.2 开工之前 |
| 采纳理由 | 评估报告 §6.2 判定为"唯一必须做的重构"。界面与 V1.1 的 agent 网关必须共用同一份校验与错误码；不下沉就会出现两份逻辑，今天一致、下个月必然漂移。越晚做，要动的冻结代码越多 |
| 影响 | 新增 `src/main/services/*`；handler 只保留取参、校验、调 service、封信封；IPC 契约与界面行为零变化；准出是门禁 6/6 + 重构前后逐文件比对结论 |

### D10 代码对 Agent 的能力形态

| 项 | 内容 |
|---|---|
| 决定 | **一层契约、多种薄壳**：业务逻辑只在主进程写一份，MCP 与 CLI 只做参数与结果转换 |
| 采纳理由 | 如果 MCP server 里再实现一套业务逻辑，它和界面必然漂移；漂移之后无法判断哪边是"对的行为" |
| 影响 | 网关是唯一实现鉴权、作用域、审批、审计、限流的地方；薄壳不写业务判断；传输可替换而不改业务 |

### D15 · V1.1.3 直链续期落点与明文 Key 迁移装配

| 项 | 内容 |
|---|---|
| 决定 | 直链续期采用方案 A（按 id 重新取单条），落点在**下载引擎发出下载请求之前**，不在入队时；续期失败一律回退库内链接并记下原因，不阻断下载 |
| 拍板日期 | 2026-11-11 00:40 |
| 拍板方式 | 依 `版本规划.md` §7.11 交付 2、`docs/密钥存储加固方案.md` §3；「下载前」按字面口径落到引擎 |
| 采纳理由 | 入队到真正下载之间可能隔很久（排队、暂停后继续），入队时续的新链接同样会过期；放在引擎里每次取任务前续期，重试也会自动重续，覆盖面更完整 |
| 续期不缓存 | 续期调用走 `fetchJson` 的 `skipCache`：签名直链本身约两天失效，命中 24 小时缓存会让链接在到期前被提前用掉，等于没修 |
| 复用既有约束 | 续期复用注册表里的同一个限流桶（Pixabay 80 次/分钟），不新开额度；批量 20 条最多多 20 次调用 |
| 错误可分辨 | 续期失败时把原因码带进最终错误：断网→`E_NETWORK`、Key 失效→`E_AUTH_REQUIRED`、续期成功但下载仍 400→`E_LINK_EXPIRED`；不再一律显示「HTTP 400」 |
| 明文 Key 迁移 | 按方案文档顺序执行：先 `wal_checkpoint(TRUNCATE)` 再留档 → 事务内 `plain:`→`enc:` → checkpoint + `VACUUM` → 强制刷新 `.bak`；留档失败不改主库，清理与备份失败只 WARN，均不阻断启动 |
| 幂等口径 | 只命中 `plain:` 前缀，已是 `enc:` 的行不动；重复启动计数为 0，`enc:` 值长度不变 |
| 本轮边界 | 只改 V1.1.3 范围内的源码、测试与文档；未动 V0.3 及以后的功能，未改 UI 风格，未装依赖，未永久删除任何文件 |
